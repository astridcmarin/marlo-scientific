# Track C: a language-model eligibility extractor (plan v3)

**Status (12 November 2026):** plan locked, prompt frozen at revision 2; run procedure added after an outside methods review; the blind check on the v2 sample waits for the owner's 200-trial annotation (plan v2). Research only; no page uses this extractor.

**What it is.** Extractor `llm-c1` gives Claude Fable (`claude-fable-5-2`) the pinned prompt (`intelligence_store/data/eligibility_extractor_llm_c1_prompt.md`, a condensed form of annotation guide v2) and one trial's registered criteria text, and takes back one JSON object per trial in the format of extractor v1.1. `intelligence_store/eligibility_extractor_llm.py` writes the input files and parses and checks the answers; an invalid answer is "no answer" and scores as not stated. The model runs in separate workspace sessions that see only the prompt and the input file.

**How it is checked.** `eligibility_validation_plan_v3.json` takes everything from plan v2 unchanged: corpus, sample, annotation export, `score_pair` and the decision rule. The 200 trials are read twice, in two independent sets of five sessions; run 1 is the primary result and run 2 measures how often the model gives the same answer. The comparison with extractor v1.1 is descriptive. A passing type is a candidate for the benchmarking page, not a feature.

**Development.** Two prompt revisions on the v1 validation sample (120 trials, already seen), recorded in `docs/development/eligibility_llm_c1_development.json` (regenerated by `scripts/eligibility_llm_c1_development.py` from the stored outputs). Guide v1 recorded exclusion comparators inconsistently, so a direction-free score is given beside plan v2's score; direction-free precision was 0.86–1.00 by type at revision 2. Revision 2 added an "other" unit for values written without one (revision 1 guessed a unit) and said that a threshold required for entry is reported even when it describes the condition studied.

**Limits.** A workspace session does not fix the model version or temperature; the identifier each session reports is recorded. The sessions run under instructions not to search the text with code, which cannot be enforced, only stated and reported.

## Run procedure (12 November 2026, committed before any run)

Adopted after the ChatGPT methods review ([reviews/2026-11_chatgpt_track_c_review.md](reviews/2026-11_chatgpt_track_c_review.md)). It sets how the runs are carried out; plan v3, the prompt, the runner and the scoring are unchanged.

1. **Isolation.** Each session works in its own folder holding only the frozen prompt and its input file (written by `eligibility_extractor_llm`). Nothing else: no annotation, guide, code, report, extractor v1.1 output or v1.1 score is ever placed where a session can read it.
2. **One fixed launch message**, the same for every session apart from the folder and file names, recorded in the result. The operator sends no other message to a session: no hints, corrections or feedback.
3. **What is kept for every session:** the full transcript and its SHA-256, the launch time, the model identifier the session reports, the input file's SHA-256, and the untouched output file and its SHA-256.
4. **Reruns** only for a technical failure (the session stops before writing its output, or the service fails), each recorded with its reason. Never a rerun because of what an output says. The first complete output of each session is the one scored.
5. **Malformed output.** Output files are never edited. A line that is not valid JSON is treated as no answer for that trial, as the plan intends; because the runner would stop on it, the handling is reported as a deviation, with the number of trials affected.
6. **Reporting.** Invalid outputs (transport, format, content) are counted separately from extraction errors; run-to-run agreement is reported for annotated-positive pairs as well as overall; precision and recall are named "the prespecified pair-based measures"; the "within normal limits" difference between prompt and guide is named as a possible source of disagreement on creatinine and AST/ALT. Results describe agreement with the owner's annotation on these registry texts, not a gold standard, generalisation or clinical use.

## Result (13 November 2026)

Report: `docs/verification/eligibility_validation_llm_c1.json`. Outputs pinned before scoring: `docs/development/eligibility_llm_c1_outputs/`; every attempt, including two stopped by the usage limit, in `docs/development/eligibility_llm_c1_run_attempts.json`.

- **No type passes** the plan v2 rule on run 1, the primary run; neither does rule-based v1.1 on the same 200 trials (`docs/verification/eligibility_validation_v2.json`).
- **Against v1.1, pair by pair:** the language model is right where v1.1 is wrong more often than the reverse in seven of eight types (for example kidney function 9 against 3); haemoglobin goes the other way (1 against 3). Recall is higher for kidney function (0.82 against 0.72), platelets (0.79 against 0.74) and ECOG (0.94 against 0.89); precision is similar. These are paired counts, not a test of superiority, and are not reported as one.
- **Repeatability:** the two runs agree on 1,596 of 1,600 type answers (99.75%); on annotated-positive pairs 658 of 661 (99.55%), and where either run returned a threshold 684 of 688 (99.42%). Agreement compares status, comparator, value and unit only. Strata, per-type counts and the four disagreements: `docs/development/eligibility_llm_c1_audit_v1.json`. No complete output had a format problem or a missing trial; 12 of 22 launched sessions stopped at the usage limit first, so results are conditional on completion.
- **Shared disagreements:** in every type, 13 to 33 trial-and-type pairs disagree with the reference for both extractors. They may reflect annotation errors, ambiguous text, differences between the prompt and the guide (such as the prompt's wider "within normal limits" rule for creatinine and AST/ALT), or errors common to both extractors; their frequency does not distinguish these explanations. An error review of the shared cases comes before any statement about either extractor's accuracy: the owner's review page is `/models/eligibility/shared-errors` (`intelligence_store/eligibility_shared_errors.py`, 166 pairs). Its decisions do not change either locked result; a correction would go into a new annotation version.

What the result may be read as, following the outside review (`docs/reviews/2026-11_chatgpt_track_c_review.md`): agreement of two frozen extraction workflows with one annotator's reading of these 200 myeloma registry texts, on comparator, value and unit only, under the prespecified pair-based measures. Not a gold standard, not generalisation to other texts, not superiority, and not suitability for screening patients.
